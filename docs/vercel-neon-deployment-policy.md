# Vercel deployment access and Neon preview database policy

This is a reusable policy for Vercel-hosted applications using Neon PostgreSQL. It is guidance, not proof that a project has been configured or that any automation has been installed. For the Agent Workspace execution contract, see [the operational runbook](https://github.com/judigot/agent-workspace/blob/main/docs/vercel-neon-preview-operations.md).

## 1. Deployment protection is a separate control from app authentication

- Vercel Authentication (deployment-level SSO), Vercel Password Protection, and Trusted IPs are separate from the application's own sign-in/authorization. Switching off the Vercel gate **does not** remove app authentication.
- Default to protected preview/development deployments where a private review experience suffices. Never disable protection solely to resolve an inaccessible API, a `403`, an OAuth redirect, or a failing automated browser test. Prefer Vercel shareable links or an approved automation-bypass mechanism for bounded access.
- When the owner **explicitly authorizes public access to an identified project**, first confirm the Vercel team, project ID, intended deployment targets, public aliases, app authentication, database contents, and whether the project has test/default passwords. Project-level protection changes may expose **existing and future** deployments, not only the latest build. Do not change unrelated projects or team defaults.
- Vercel Dashboard: select the project -> **Settings -> Deployment Protection -> Vercel Authentication** -> disable -> save. With the authorized Vercel project-update API, set `ssoProtection` to `null`. Do **not** change `passwordProtection`, `trustedIps`, or other settings without explicit matching scope.
- Confirm by rereading the project and checking SSO disabled; inspect Password Protection and Trusted IPs independently. Verify the intended URL from a clean unauthenticated client **without** a share link, bypass token, Vercel session, or cached auth cookie. A successful fetch through a privileged connector is not proof of public access.
- Keep application session enforcement on the server. Before opening the site publicly, remove/rotate default or publicly disclosed credentials, use a non-production/sanitized database, and check for privileged unauthenticated routes. If a deliberately temporary test still uses known credentials, disclose the risk and do not call it production-secure.
- For production websites intended to be public, choose the narrowest Vercel protection scope; preview URLs can stay protected while the production domain is public. Disabling project-wide SSO is not a universal deployment step.

Reference: [Vercel Authentication and API disable setting](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/vercel-authentication) and [Deployment Protection scope](https://vercel.com/docs/deployment-protection).

## 2. Neon database branches for PRs and branches

- A Vercel Preview Deployment is **not** automatically a separate database. A dedicated Neon integration or trusted provisioning automation must create and connect the correct database branch.
- **Preferred when persistent state per PR is required:** one Neon branch for each logical PR, reused across commits and preview redeploys. Key identity by repository plus PR number, not the number alone (for example `preview/<repo-slug>/pr-123`). For a feature branch without a PR, use a deterministic sanitized repository/branch identity. Keep a durable mapping to the actual Neon branch ID; never infer deletion targets only from a mutable branch name.
- **Native Neon/Vercel integration:** a Vercel-managed Marketplace integration or Neon-managed Connected Accounts integration can provision preview branches and inject database connection variables. This can work with an **existing Neon organization** and does not require moving the Vercel project to a different organization. Verify its actual branch reuse, lifecycle, environment scope, and billing configuration in the currently installed integration before relying on it.
- **GitHub Actions + Neon API:** a trusted workflow may create/reuse a Neon preview branch at PR open/update, migrate/seed it, scope its secret connection string to the intended Vercel preview/deployment, verify that deployed SHA uses that branch, and clean it up after PR close. This is a separate implementation option; do not enable both lifecycle controllers for the same environment.
- Derive preview data from an empty or sanitized baseline, not an unrestricted copy of sensitive production data. Treat storage/compute costs and retention as real resources. Run migrations against the isolated branch, never against production as part of preview setup.
- Inject `DATABASE_URL` only through encrypted environment configuration or a secure deployment environment, never tracked `.env` files, PR comments, job logs, or static frontend variables. A branch-scoped preview credential **does not** populate the Vercel Production environment after a PR merges.
- Before a production merge can trigger deployment, independently verify Production secrets, migration strategy, build checks and the intended production database. Successful CI and a `READY` deployment do not prove authenticated end-to-end functionality.
- Verify a real preview test: deployment SHA, environment-to-Neon-branch identity, database connectivity, schema, login, denied unauthorized access, create/read/update/delete persistence, and logout. Direct database SQL CRUD by itself is **not** live UI CRUD verification.
- On PR close, clean up **only** the provisioned preview branch after identifying its tracked resource ID, checking no live deployment still needs it, and honoring the selected integration's retention rules. Never delete a production/default Neon branch; fail closed on ambiguous ownership.
- Treat fork PR code as untrusted; do not pass Neon admin credentials, deploy tokens, or other privileged secrets to unreviewed PR workflows. Provision/configure from trusted code with least privilege and separate secret-bearing stages from untrusted builds.

References: [Neon Vercel integration and per-preview branching](https://neon.com/blog/neon-vercel-native-integration), [Neon-managed versus Vercel-managed integrations](https://neon.com/blog/auth-that-just-works-in-vercel-previews), [Neon preview branch lifecycle and reuse](https://neon.com/blog/big-dx-improvements-for-neon-users-on-vercel), and [GitHub Actions preview workflow](https://neon.com/blog/branching-with-preview-environments).

## 3. Evidence and status vocabulary

- Record the selected database lifecycle owner (`native_integration` or `trusted_actions`), exact app repo/PR/branch/commit, Vercel team/project/deployment, Neon project/branch ID, desired environment scope, and verified state **without** credential values.
- Separate statuses: `not_configured`, `provisioned`, `migrated`, `deployment_ready`, `live_verified`, `blocked`, and `cleaned`. Do not report an unimplemented design as automatic, or database-only tests as live UI verification.
- If the current connector lacks integration-installation privileges, secure environment-variable writes, or browser execution, report the missing capability and preserve existing resources rather than silently falling back to shared production credentials.
